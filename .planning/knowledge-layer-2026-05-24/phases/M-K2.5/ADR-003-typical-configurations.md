# ADR-003 — Typical Configurations Knowledge

**Status:** Accepted
**Date:** 2026-05-26
**Decider:** Никита Хворостов (user) + Claude (architect)
**Milestone:** M-K2.5

## Context

После закрытия M-K2 пользователь поднял запрос на **глубокое понимание
логики типовых конфигураций 1С** (УТ, ERP, КА, БП, ЗУП, УСО,
Документооборот). Текущая система умеет индексировать клиентскую базу
через MCP в реальном времени, но не имеет преднакопленных знаний о том
как устроены типовые. Это даёт два конкретных юзкейса:

1. **Аналитик без подключённой базы** — спросить «как в УТ работает X»
   и получить ответ прямо в чате, без подключения MCP к базе.
2. **GAP-анализ** — сравнить клиентский объект с типовым и сказать
   «вот что доработано относительно типовой УТ 11.5.18.193».

Эти юзкейсы блокированы отсутствием знаний о типовых.

## Decisions

### D1 — Snapshot-based индексация, не live

**Решение:** разбираем фиксированные версии типовых, фиксируем snapshot в
БД. Live-индексация при подключении клиентской базы — отдельный путь
(он уже работает через MCP).

**Обоснование:**
- Live = 4-7 дней индексации каждый раз → неприемлемо для UX
- Типовые меняются медленно (релиз каждые 2-4 месяца), snapshot валиден
- Клиент с расхождением версий получает fallback на ближайшую известную

**Trade-off:** клиент на УТ 11.5.20.X получит ответы по УТ 11.5.18.193 —
небольшие расхождения возможны, но в 90% случаев логика та же.

### D2 — Reserved channel namespaces

**Решение:** каждой типовой выдаётся фиксированный channel_id с префиксом
`_<kind><version>_<patch>` (например `_ut115_18_193`).

**Обоснование:**
- Реальные MCP-каналы используют UUID v4, никогда не начинаются с `_`
- Соблюдён существующий паттерн: `_its` (ИТС), `_bsp` (БСП)
- Один и тот же объект `Документ.РеализацияТоваровУслуг` может
  существовать в УТ 11.5 и в ERP 2.5 одновременно — namespace разводит

**Соглашение:**
- `_ut115_<minor>_<patch>` — Управление торговлей 11.5.x.y
- `_erp25_<minor>_<patch>` — ERP 2.5.x.y
- `_ka2_<minor>_<patch>` — Комплексная автоматизация 2.5.x.y
- `_bp30_<minor>_<patch>` — Бухгалтерия предприятия 3.0.x.y
- `_zup31_<minor>_<patch>` — Зарплата и управление персоналом 3.1.x.y
- `_uso25_<minor>_<patch>` — Управление строительной организацией 2.5.x.y
- `_docflow3_<minor>_<patch>` — Документооборот 3.x.y

### D3 — Embedding только LLM-описаний

**Решение:** в OpenAI embedding API уходят только русскоязычные
описательные карточки (что делает объект, какие движения, типовые
сценарии). Сам BSL-код типовых хранится **локально** и в облако
**не отправляется**.

**Обоснование:**
- Лицензионное соглашение 1С имеет пункты по обработке защищённого кода
- Передача BSL-кода типовой 1С во внешний API — серая зона
- Карточки на русском — это аналитическая работа, лицензия 1С на анализ
  не распространяется
- Embedding описаний даёт 90% качества поиска относительно embedding кода

**Trade-off:** теряем возможность найти точное место в коде по семантике —
но граф вызовов (M-K2.5.4) даёт точные ссылки через AST.

### D4 — Шесть графов поверх одной типовой

**Решение:** для каждой типовой строим 6 разных графов в общем
`graph_storage` (использует фундамент M-K3.17.1a):

1. **CALLS** — метод A вызывает метод B
2. **CONTAINS** — модуль содержит метод, документ содержит реквизит
3. **USES** — метод использует тип / справочник
4. **WRITES_TO** — документ → регистр через `Движения.X.Записать()`
5. **READS_FROM** — отчёт → регистр через запрос
6. **REFERENCES** — реквизит → справочник через тип

**Обоснование:**
- Один универсальный граф = смесь семантически разных связей =
  неинтерпретируемые traversal-запросы
- Разделение по типам = чистый интерфейс: «найди всё что пишет в
  РегистрНакопления.ТоварыНаСкладах» = filter edge_kind=WRITES_TO

**Trade-off:** больше edge-ов в БД (×6 в худшем случае), но recursive CTE
справится — индексы по (channel_id, edge_kind) есть.

### D5 — Парсим всё что выгружается DESIGNER'ом

**Решение:** при выгрузке `.dt → DumpConfigToFiles` парсим все
полученные файлы. Защищённые модули технически выгружаются с пустым
телом (только сигнатура) — это техническое ограничение 1С.

**Обоснование:**
- Лицензионно у пользователя есть право на конфигурацию
- DESIGNER сам решает что отдаёт — мы парсим выход
- Защищённые модули даёт ~5-25% пропусков (УТ/БП мало, ERP/КА больше)

**Trade-off:** карточки защищённых модулей будут содержать пометку
«логика недоступна — защищённый код». Это честно и полезно.

### D6 — СКД отчёты разбираем глубоко

**Решение:** парсим весь XML СКД — запросы, настройки, ресурсы,
вычисляемые поля, варианты, шаблоны.

**Обоснование:**
- Отчёты — главный потребитель регистров → без них граф READS_FROM
  будет неполным
- В типовых ~500-1500 отчётов
- Только текст запросов = поверхностно

**Trade-off:** парсинг XML СКД сложнее парсинга BSL — добавим
библиотеку lxml или встроенный xml.etree.

### D7 — Параллельно с M-K3, не вместо

**Решение:** M-K2.5 идёт параллельной веткой с M-K3 (Relational +
Behavioral). M-K3 продолжается с phase 17.1b (graph extractor для
клиентских баз).

**Обоснование:**
- Фундамент graph_storage общий — уже готов (M-K3.17.1a)
- Контент независим: M-K3 работает с клиентской базой клиента
  через MCP, M-K2.5 — со снапшотами типовых
- Не блокируем M-K3 на 4-6 месяцев

**Trade-off:** одновременно две большие ветки — нужна дисциплина
по атомарным коммитам и регулярному merge в main.

## Consequences

### Положительные

- Бот может ответить «как работает X в УТ» без подключения базы
- GAP-анализ становится возможным
- Юридическая чистота — код типовых не уходит в OpenAI
- Расширяемость — новый типовой добавляется через тот же пайплайн

### Отрицательные

- Долгий milestone — 4-6 месяцев на 7 конфигураций
- Зависимость от LLM-токенов на этапе карточек ($200-3000 на 7 конф)
- Snapshot устаревает — нужен процесс обновления при релизах 1С

### Нейтральные

- Дополнительные миграции v17+ к схеме БД
- Новый namespace в frontend для типовых
- Расширение graph_storage usage patterns

## Альтернативы рассмотренные

### A1 — Не делать вообще

**Отвергнуто:** пользователь явно сказал «нужно качество, будем
это тоже делать».

### A2 — Делать в M-K3, не отдельным milestone

**Отвергнуто:** M-K3 = клиентский граф через MCP, M-K2.5 = снапшоты
типовых. Разные пайплайны, разные дедлайны. Параллельная ветка чище.

### A3 — Live-индексация типовой при первом подключении

**Отвергнуто:** 4-7 дней индексации каждой типовой пользователем —
неприемлемо.

### A4 — Embedding кода через локальный BGE-M3

**Отложено в M-K5:** требует GPU и +1-2 недели на пайплайн. Сейчас
эмбедим описания, в M-K5 (distribution + локальные модели) пересмотрим.

### A5 — Один универсальный граф без разделения по типам edge'ов

**Отвергнуто:** теряем семантику. См. D4.

### A6 — Парсить только модули объектов, не общие модули

**Отвергнуто:** бизнес-логика типовых в основном в общих модулях
(`УчётНДС`, `РасчётСебестоимости`). Без них картина неполна.
