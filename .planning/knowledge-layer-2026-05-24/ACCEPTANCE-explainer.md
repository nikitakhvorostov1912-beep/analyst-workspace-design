# Критерии приёмки «Объяснителя» — реально ли это поможет

> Спецификация приёмки для grounded-ИИ (граф типовой + MCP базы клиента).
> Цель документа — честно ответить «поможет ли это аналитику» и превратить
> ответ в **измеримые гейты**, а не в ощущение. Создан 2026-05-30.
> Контекст: `phases/M-K3/17-graph-accuracy/SUMMARY.md` (что построено и доказано).

---

## 0. Честный вердикт: поможет — но при ОДНОМ условии

**Поможет реально**, но ценность **условна, и условие — не точность, а ДОВЕРИЕ.**

Граф мы починили (факты достоверны — движения 44/44 без галлюцинаций). Но
правильный по фактам инструмент **не равно** полезный. Разберём честно:

- **Где точно поможет:** онбординг в незнакомую типовую, «что делает этот
  документ/обработка», «откуда эта цифра/движение», impact «что затронется» —
  **когда логика типовая**. Тут он меняет 15–60 мин копания в Конфигураторе/ИТС
  на секунды с пруфами. Это уже окупает продукт.
- **Где поможет частично:** диагностика ошибок — локализует «где искать»
  (симптом из MCP + механизм из графа), но при доработке только сужает зону.
- **Где НЕ поможет / ОПАСЕН:** сильно доработанные участки; вопросы, требующие
  чтения кастомного кода; ответы, где типовое выдаётся за клиентское.

**Главный риск, который решает судьбу продукта — НЕ покрытие, а калибровка.**
Большинство реальных баз клиентов доработаны. Один **уверенно неправильный**
ответ на том, что аналитик не может быстро проверить, → аналитик обжёгся →
перестал доверять → продукт мёртв. Инструмент, который честно говорит «это по
типовой, у вас может отличаться» / «не знаю», — аналитик использует как быстрый
первый проход, даже если он неидеален.

> **Следствие для приёмки:** честность/калибровка (G0, G2) весит ВЫШЕ сырой
> точности (G1). Лучше «не знаю», чем уверенная дезинформация.

**Что делает его по-настоящему полезным:** не граф сам по себе, а связка
**граф (как должно быть) + MCP (как есть в этой базе) + честная пометка
источника**. Граф в одиночку = «знание о типовой»; ценность — в совмещении с
реальностью клиента под честным ярлыком.

## 1. Что значит «помогает» (определение, чтобы было что мерить)

Аналитик получает пользу, если ответ:
1. **Достоверен** — без выдуманных фактов (объекты/методы/регистры/роли/числа).
2. **Честен по источнику** — помечено: «по типовой» / «из базы клиента» /
   «не подтверждено».
3. **Полон** — отвечает на заданный вопрос, не половину.
4. **Действенен** — аналитик может что-то сделать с ответом (а не «эссе вокруг»).
5. **Быстрее ручного** — иначе проще открыть Конфигуратор.

Якорная метрика: **время на задачу с инструментом vs без** + доля задач,
решённых верно. Всё остальное — прокси к этому.

## 2. Карта «где поможет» (честно, по типам вопроса)

| Вопрос аналитика | Типовой объект | Доработанный объект |
|---|---|---|
| Что это за документ / как работает | ✅ полно | ⚠️ типовая основа + «есть отличия» |
| Как работает обработка | ✅ полно | ⚠️ типовая основа |
| Куда пишет движения / что вызывает | ✅ из графа | ⚠️ типовая часть |
| Откуда цифра в отчёте | ✅ трассировка | ⚠️ типовая часть |
| Impact «что затронется» | ✅ (типовой охват) | ⚠️ без кастомных связей |
| Почему роль не видит объект (RLS) | ✅ полно | ⚠️ типовая часть |
| **Где ошибка** (локализация) | ✅ симптом+механизм | ⚠️ сужает зону, не читает код |
| Что **фактически** сделал в базе | ✅ через MCP | ✅ через MCP |
| Прочитать текст кастомного кода | — | ⛔ нет (исходники не берём) |

## 3. Гейты приёмки (4 уровня; G0/G2 — критичнее G1)

### G0 — Жёсткие гейты (must; не выполнено → НЕ релизим)
Бинарно, на каждый ответ:
- **G0.1 Ноль выдуманных фактов.** Каждый названный объект/метод/регистр/роль/
  условие/число присутствует в результате инструмента. *Замер:* diff
  сущностей-ответа vs сущностей-инструмента = 0 лишних (как сверка 44 док).
- **G0.2 Метка источника.** Каждое утверждение помечено «типовая» / «база
  клиента» / «не подтверждено».
- **G0.3 Нет молчаливого провала.** Либо grounded-ответ, либо честное «не нашёл,
  уточни X». Никаких циклов до лимита раундов без ответа *(текущий дефект Q2 —
  это нарушение G0.3, блокер приёмки)*.
- **G0.4 Гард типовое≠клиент.** При ответе про базу клиента, если объект может
  быть доработан — пометка «по типовой; проверь доработки» (в идеале — проверка
  структуры через MCP).

### G1 — Точность на golden-set
- Корпус ≥30 **реальных** вопросов из практики (Транзит/УСО/Век), у каждого —
  известный эталонный ответ.
- **Метрика:** доля ответов, где все grounded-факты верны И полны (нет пропуска
  критичных пунктов). Цель ≥90%, при G0.1 = 100% (ноль галлюцинаций — твёрдо).

### G2 — Калибровка / честность (anti-bullshit)
- Подмножество вопросов, где **данных нет** или объект кастомный.
- **Метрика:** доля, где инструмент верно говорит «не знаю / это доработка / нет
  данных» вместо выдумки. Цель ≥95% (критично для доверия).
- Точность меток источника ≥95%.

### G3 — Полезность (слепой тест с живыми аналитиками)
- N аналитиков × M реальных задач, с инструментом vs без (A/B).
- **Метрики:** медианное время (цель ≥3× быстрее на покрытых типах);
  корректность решения (не хуже ручной); доверие («снова воспользуешься?» 1–5,
  цель ≥4).
- **Kill-критерий:** если аналитик сообщает, что был **введён в заблуждение**
  уверенным неверным ответом → регрессия G0 → блокер, не релизим.

|---|---|---|---|

## 5. Golden-set — как собрать (нужен пользователь)

Корпус **обязан** быть из реальной практики, не синтетика. Шаблон записи:
```
Вопрос (как реально спросил аналитик): ...
Конфигурация + версия: УТ 11.5.x / ERP 2.5 / ...
Объект: типовой / доработан
Эталонный ответ (что верно): ...
Источник эталона: код типовой / данные базы / эксперт
Тип: объяснение | движения | impact | RLS | диагностика
```
Минимум 30 (по ~6 на UC), из них ≥8 — про **доработанные** объекты и ≥5 — где
**ответа нет** (для проверки G2 «честное не знаю»). Готов помочь собрать —
вытащить кандидатов из практики Транзит/УСО.

## 6. Failure modes — что НЕ должен делать (→ привязка к гейтам)

1. Выдумывать факты (имена, методы, условия, числа) → **G0.1**.
2. Выдавать типовое за клиентское без пометки → **G0.4 / G2**.
3. Молчать / зацикливаться без ответа → **G0.3** *(текущий дефект Q2)*.
4. Уверенно отвечать при отсутствии данных → **G2**.
5. Топить ответ в «глоссах» (общие знания модели вместо факта) → **G1/действенность**.
6. Давать impact только по типовой, не предупредив про кастомные связи → **G0.4**.

## 7. Как проверяем «помогает» (eval-харнесс)

1. **Golden-set прогон** (детерминированно, как `grounding_harness`): каждый
   вопрос → grounded-ответ → авто-скоринг G0.1 (diff сущностей) + ручная сверка
   G1/G2. Уже есть основа: `scripts/grounding_harness.py` + `_mimo_diff.txt`.
2. **Слепой тест аналитиков** (G3): протокол A/B на реальных задачах, замер
   времени/корректности/доверия.
3. **Регрессия:** golden-set гоняется после каждой правки промпта/графа.

---

## 8. Решение-гейт (когда «годен к показу клиенту»)

- **G0 не пройден** (галлюцинации / молчание / нет меток) → **НЕ показываем**,
  это анти-доверие.
- **G0+G2 пройдены, G1 ≥90%, G3 ≥3× по времени и доверие ≥4** → годен к пилоту.
- **G3 слабый** (аналитики не доверяют / не быстрее) → итерируем промпт/карточки
  или **сужаем заявку** (честно: «только типовая, только эти типы вопросов»).
- Честный kill: если после 2–3 итераций доверие не растёт — фича не вытягивает
  как самостоятельная, переносим ценность в узкий сценарий (напр. только
  «откуда движения/цифра» — самый надёжный).

---

## 9. TL;DR для роадмапа

«Объяснитель» **реально поможет**, если пройдёт **G0 (ноль галлюцинаций + метки
источника + не молчит) и G2 (честное "не знаю")** — это весит выше точности.
Сейчас: движения/RLS проходят G0/G1 на единичных вопросах; цепочка вызовов
нарушает G0.3 (дефект #38 — чинить); golden-set из практики ещё не собран (нужен
пользователь). Релиз клиенту — только после golden-set прогона + слепого теста.
